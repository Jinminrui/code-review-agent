# Review Workbench UI Design

- 日期：2026-06-07
- 目标：定义审查会话主工作台的高保真 UI 方案，并约束 renderer 侧实现边界
- 范围：`packages/review-app` 中与 `review-session-page`、会话级布局、finding 列表、摘要面板、diff 阅读台直接相关的界面

## 1. 设计目标

本次 UI 设计只解决一个核心问题：让 reviewer 在一次本地代码审查中，以最短路径完成“理解改动”与“验证问题”两件事。

本方案服务的是主工作台，不覆盖仓库/分支选择页和设置页的重设计。它必须建立在现有产品基线之上：

1. 主工作台是整个 MVP 的核心场景。
2. 左侧负责摘要、风险聚焦与 finding 流。
3. 右侧负责 diff、代码上下文与定位验证。
4. 产品定位是“桌面端可视化代码审查 Agent”，不是通用后台，也不是 AI 报告页。

这次改版追求的不是“更华丽”，而是让界面更像一张可工作的审查桌面：能快速扫描、能自然切换线索、能诚实表达定位置信度。

## 2. 体验原则

### 2.1 完成态优先，保留流式痕迹

主画面以“审查已完成后的高效核查”作为优先场景，用户进入页面后应首先看到结构化结论与问题流，而不是巨大的运行态提示。

同时，界面仍需保留 Agent 刚刚工作过的动态痕迹，例如：

1. 已完成多少审查单元。
2. 最近一次流式事件发生时间。
3. 当前 session 是 running 还是 completed。

这些信息用于建立“这是一个渐进式工作的审查系统”认知，但视觉权重要低于 findings 和 diff 验证流程。

### 2.2 工作台感高于后台感

界面必须避免通用 CRUD 管理台的观感。判断标准：

1. 不以大面积统计卡片作为主内容。
2. 不把核心交互藏在弹窗中。
3. 左侧不是功能菜单堆叠，而是一条有审查节奏的脉络栏。
4. 右侧不是单纯的编辑器嵌入，而是“证据阅读台”。

### 2.3 平衡型信息密度

用户已明确选择平衡型密度，因此主工作台应满足：

1. 左侧一屏内能看到 session 头部、摘要和部分 finding。
2. 每张 finding 卡片必须有足够信息支持快速判断，但不强迫用户阅读大段正文。
3. 页面保留呼吸感，依赖层级和间距而不是海量容器制造秩序。

### 2.4 可信度优先

UI 必须服务于架构文档中“定位失败则降级为文件级 finding”的原则：

1. 行级 finding 要清晰标注并准确滚动定位。
2. 文件级 finding 不能伪装成精确命中某一行。
3. 右侧详情区要显式说明当前展示的是 line-level 还是 file-level 上下文。

## 3. 整体布局

### 3.1 三层工作台结构

主工作台采用三层结构，而不是单纯两栏：

1. `全局导航壳`
   左侧窄栏，承载产品名和全局入口，例如工作台、历史会话、设置。它的职责是提供稳定框架，不承载本次 review 的主要信息。
2. `审查控制栏`
   中间栏，宽度建议在 380-420px 的感受区间内，承接本次 session 的头部信息、流式痕迹、摘要、风险文件和 finding 流。
3. `证据阅读台`
   右侧主区域，承载当前选中 finding 的上下文、证据摘要和 Monaco diff。

该结构必须与现有实现兼容：保留 `AppShell + ReviewSessionPage` 的页面骨架，不引入新的顶层页面模式。

### 3.2 布局职责

各区职责固定：

1. 全局导航壳回答“我在什么产品里”。
2. 审查控制栏回答“本次 review 看什么、先看什么”。
3. 证据阅读台回答“当前这条问题如何验证”。

任何实现都不应让右侧承担摘要职责，也不应让左侧承担大段代码阅读职责。

## 4. 视觉方向

### 4.1 总体气质

本次采用“编辑台方向”：

1. 气质介于专业代码工具与研究型工作台之间。
2. 关键词：温和、稳定、可读、克制、可信。
3. 不使用通用紫渐变、霓虹 glow 或过强的 SaaS 科技感。

### 4.2 色彩系统

基础色建议围绕三类角色组织：

1. `暖灰纸面`
   作为主背景与面板底色，建立“桌面 / 纸面 / 审查台”的温度。
2. `深墨文本`
   作为标题、正文、代码周边文本的主色，保证长时间阅读稳定。
3. `锈橙风险色`
   作为风险强调、当前选中态和关键信号色，替代高饱和警示红的泛滥使用。

允许存在少量灰蓝或烟灰作为次级信息辅助，但不应扩展出过多强调色。

### 4.3 材质与边界

界面不应依赖大量厚卡片建立层次，应优先使用：

1. 明度差。
2. 细边线。
3. 间距分组。
4. 局部圆角容器。

只有真正需要强调的模块，例如当前 finding、摘要主结论、右侧证据条，才使用更明确的容器轮廓。

### 4.4 排版

正文与工具文本以高可读 sans-serif 为主，支持中文环境下的稳定阅读。标题与会话头部允许适度增强字重、字距和层级反差，但不能为了风格破坏工具效率。

## 5. 左侧审查控制栏

左侧不是四张互不相干的卡片，而是一条按审查路径组织的信息流。

### 5.1 会话头部

位于左栏最顶部，包含：

1. Session 标题或默认名称。
2. 仓库名。
3. `base -> target` 分支关系。
4. 发起时间或最近更新时间。
5. 当前状态 badge。

该区域需要像“案件封面”而不是表单结果回显，重点是让用户快速建立本次审查对象的上下文。

### 5.2 流式进度条带

位于会话头部下方，展示轻量的执行痕迹，包括：

1. 已处理审查单元数量。
2. 剩余或待处理状态。
3. 最近一次事件，例如刚完成某个 review unit。

该区域的任务是保留渐进式系统的生命感，而不是成为页面主焦点。

### 5.3 审查摘要区

摘要区不使用孤立的三宫格数字卡作为唯一表现，而是由两层信息组成：

1. 主结论句，概括本次改动集中在哪里、风险主要落在哪。
2. 辅助指标，例如变更文件数、finding 总数、高风险数。

如果主结论句暂时没有后端字段支持，前端第一版可用更具叙述性的标题与指标组合模拟，但不得编造不存在的业务结论。

### 5.4 高风险文件带

高风险文件区承担“优先查看入口”角色。每条文件项应至少展示：

1. 文件路径或短文件名。
2. 风险热度或 severity 聚合信号。
3. 关联 finding 数量。

它的气质更接近“优先现场导航”而不是普通文件列表。

### 5.5 Finding 流

finding 列表是左栏主角，每张卡片至少包含四层信息：

1. 严重级别与类别标签。
2. 一句话摘要。
3. 文件路径与行号或文件级状态。
4. 一行证据、说明或建议。

选中态必须足够明确，且不能依赖过时的“彩色左边框 accent 卡片”模式。更合适的信号包括：

1. 容器边框加深。
2. 背景明度变化。
3. 当前项标记点或局部强调条。

### 5.6 过滤与切换

finding 流顶部应预留轻量筛选能力，优先支持：

1. 全部 / 高风险。
2. 行级 / 文件级。
3. 按 severity 聚焦。

即便第一版实现不完整，结构上也应为该区域预留稳定位置。

## 6. 右侧证据阅读台

### 6.1 上下文顶栏

右侧顶部需要一个明确但轻量的上下文栏，至少展示：

1. 当前文件路径。
2. 当前 finding 标题或摘要。
3. 严重级别。
4. 定位状态（line-level / file-level）。

这样用户从左侧进入代码时，不会失去“我正在验证什么”的上下文。

### 6.2 证据摘要条

在 Monaco 上方增加一条较窄证据区，用于展示：

1. evidence 的核心句子。
2. suggestion 的一句摘要。
3. 当 evidence 缺失时，展示 explanation 的节选。

这条信息的职责是让 reviewer 在进入代码前先理解指控点，而不是直接沉入 diff。

### 6.3 Diff 主阅读区

Monaco diff 是主阅读区，视觉上应是整页最安静的区域。设计要求：

1. 行级 finding 提供精确 reveal 和明确但克制的高亮。
2. 文件级 finding 采用文件级说明和上下文范围强调，不假装命中某一行。
3. diff 区容器需与外部壳层拉开层次，但不能堆叠多余装饰。

### 6.4 空状态

未选择 finding 时，右侧空状态仍需保持工作台感。空状态应：

1. 引导用户从左侧选择一条 finding。
2. 显示该区将承载的内容类型，而不是仅写“暂无数据”。
3. 保持低干扰，不抢左侧焦点。

## 7. 交互要求

### 7.1 选中与定位

当用户点击 finding 卡片时：

1. 左侧必须保持明确选中态。
2. 右侧自动切换到对应文件 diff。
3. 如果是行级 finding，Monaco 以舒适阅读位置 reveal 到对应代码段。
4. 如果是文件级 finding，右侧顶栏与证据摘要条明确说明是文件级核查。

### 7.2 状态切换

当 session 从 running 进入 completed：

1. 流式状态区域更新为完成态。
2. finding 流保持稳定，不应整页跳动。
3. 右侧当前已打开的上下文应尽量保留。

### 7.3 长列表与滚动

左侧控制栏允许内部滚动，但会话头部与主要筛选区应尽量保持靠上稳定，避免用户在长 finding 流中反复迷失。

## 8. 实现约束

本次 UI 设计需遵守现有仓库约束：

1. 不引入超出当前计划范围的大规模新框架。
2. 优先在 `packages/review-app/src/components/session`、`components/layout`、`pages/review-session-page.tsx` 内演进。
3. 继续通过结构化数据驱动，不在前端猜测后端未提供字段。
4. 若某些设计信息暂时缺少数据支撑，允许采用保守降级，而不是伪造内容。

## 9. 第一阶段落地范围

为了避免范围扩散，第一阶段实现只要求完成：

1. `AppShell` 的全局壳层升级。
2. `ReviewSessionPage` 的三层工作台布局。
3. 左侧会话头部、流式状态、摘要区、风险文件区、finding 流的视觉重组。
4. 右侧上下文顶栏、证据摘要条、空状态与 Monaco 外层阅读台包装。
5. 基础的 selected finding 联动与文件级状态表达优化。

以下内容可以留在后续迭代：

1. 更复杂的 finding 筛选逻辑。
2. 面板拖拽调整宽度。
3. 动画与高级过渡。
4. 历史页和启动页的统一重设计。
