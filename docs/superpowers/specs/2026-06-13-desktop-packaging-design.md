# 桌面端打包与发布链路设计

**日期**：2026-06-13  
**状态**：草案  
**作者**：Code Review Agent Team

## 概述

本设计文档描述 `Code Review Agent` 从当前开发态 Electron 工程演进为可交付桌面软件的方案。第一阶段目标是产出可安装的 `macOS DMG`，同时让工程结构、构建脚本和打包配置为后续 `Windows` 支持保留清晰扩展位。

## 背景

当前仓库已经具备桌面应用的核心运行形态：

1. 存在独立的 Electron 壳包 `packages/review-shell`
2. renderer 由 `packages/review-app` 提供
3. 审查引擎由 `packages/review-backend` 提供
4. 根目录已有 workspace 级 `build`、`test`、`typecheck` 脚本

当前缺口主要不在“是否是桌面应用”，而在“如何把开发态 Electron 工程稳定收敛为正式桌面安装包”。现状下：

1. renderer 默认通过开发服务器地址加载
2. 还没有正式打包工具链
3. 还没有面向安装包分发的资源组织与路径约束
4. 还没有发布阶段的产物边界和验证标准

## 设计目标

1. 首发支持生成可安装的 `macOS DMG`
2. 保持现有 `Electron + TypeScript + pnpm workspace` 架构，不引入额外服务层
3. 明确区分开发态与生产打包态的 renderer 加载方式
4. 让 `review-shell` 继续作为唯一桌面应用入口
5. 配置层为未来 `Windows` 打包预留扩展位，但本阶段不实现 Windows 产物

## 非目标

本次方案明确不包含以下能力：

1. 自动更新
2. GitHub / GitLab 在线分发集成
3. macOS 签名与 notarization 的完整闭环落地
4. Windows 安装包实现
5. 围绕打包目标对前后端业务逻辑做大规模重构

## 方案选型

本次打包方案建议采用 `electron-builder`。

### 备选方案对比

#### 方案一：`electron-builder`（推荐）

优点：

1. `DMG` 目标成熟，适合正式桌面软件交付
2. 产物目录、应用名、图标、平台区分配置集中
3. 后续补 `Windows` 时可以平滑增加 `nsis`
4. 更适合当前已存在的自定义 workspace 结构

代价：

1. 需要补一层正式构建与打包脚本
2. 需要明确生产态资源加载方式

#### 方案二：`electron-forge`

优点：

1. 官方生态统一
2. 适合新建 Electron 项目

代价：

1. 对当前自定义 `pnpm workspace + tsc + Vite` 结构适配成本更高
2. 不一定比 `electron-builder` 更省改造量

#### 方案三：手工拼接 `electron-packager + dmg` 工具

优点：

1. 灵活

代价：

1. 脚本分散
2. 后续签名、公证、多平台支持维护成本高
3. 不适合当前阶段的 MVP 工程目标

## 总体方案

### 1. 打包目标与产物边界

首发交付物分为两层：

1. 用户安装产物：`Code Review Agent.dmg`
2. 构建中间产物：`review-app` 静态资源、`review-shell` 主进程产物、`review-backend` 运行时代码以及 `electron-builder` 输出目录

边界约束如下：

1. `review-shell` 继续作为唯一 Electron 入口
2. 根目录统一编排构建与打包
3. 开发态与生产态的 renderer 加载逻辑必须显式分离
4. 首发不把自动更新纳入范围

### 2. 工程改造方向

#### 2.1 生产态 renderer 入口切换

当前 `packages/review-shell/src/runtime-config.ts` 默认返回开发服务器地址，适合本地联调，但不适合安装包运行。

打包后需要支持两种运行模式：

1. 开发态：继续加载 `REVIEW_RENDERER_URL`
2. 生产态：加载本地静态文件入口

这里的关键不是单纯改 URL，而是建立稳定的“运行模式识别 + 资源路径解析”机制，避免打包后因找不到 renderer 入口导致白屏。

#### 2.2 资源组织方式

建议把 `review-app` 的构建产物作为静态资源打入 Electron 应用，把 `review-shell` 和 `review-backend` 的构建结果作为应用代码一并打包。

这样可以保持当前三层职责不变：

1. `review-shell` 负责主进程、preload、窗口和 IPC
2. `review-app` 只提供 renderer 静态资源
3. `review-backend` 继续作为主进程内可调用应用服务

#### 2.3 根目录脚本分层

建议保留现有 workspace 级 `build`，并新增两层脚本职责：

1. `build:desktop`
   用于为桌面打包准备完整产物
2. `dist:mac`
   用于调用 `electron-builder` 生成 `macOS DMG`

这样开发、编译、打包三条路径边界更清晰：

1. `dev:desktop` 服务本地开发
2. `build` 服务工程编译校验
3. `dist:mac` 服务正式安装包输出

#### 2.4 打包配置位置

建议把 `electron-builder` 配置放在仓库根部的集中位置，例如根 `package.json` 或独立配置文件。

原因：

1. 打包配置天然跨 `review-shell`、`review-app`、`review-backend`
2. 根目录更适合统一声明输出目录、文件范围和平台目标
3. 未来扩展 `Windows` 时，不需要把平台配置散落到多个包

配置至少应覆盖：

1. `appId`
2. `productName`
3. 输出目录
4. 打包文件范围
5. 静态资源映射
6. `mac.target = dmg`
7. 未来 `win.target = nsis` 的扩展位

### 3. 平台扩展策略

本阶段只实现 `macOS DMG`，但从结构上预留 `Windows`。

建议的策略是：

1. 脚本层先只提供 `dist:mac`
2. 配置层预留 `mac` / `win` 分区
3. 图标、安装器、路径校验按平台分开管理

这样后续扩展 `Windows` 时，主要新增的是平台专属资源和安装器配置，而不是推翻现有打包结构。

## 风险与约束

### 1. 开发地址与本地文件切换风险

这是首要风险点。若生产态仍依赖 `http://127.0.0.1:5173`，打包后的应用将无法在离开开发环境后运行。

要求：

1. 运行时必须显式区分开发态和生产态
2. 不依赖隐式环境假设

### 2. 路径解析风险

开发态可以假设仓库目录存在，但打包后运行路径会变为 `.app` 内部资源目录。

要求：

1. preload、renderer 入口、应用图标及其他内置资源统一走运行时路径解析
2. 禁止写死只在仓库目录可用的相对路径

### 3. 数据写入位置约束

会话存储、缓存和导出文件不能依赖应用安装目录。

要求：

1. 持久化数据继续使用 `app.getPath("userData")`
2. 不把运行时写入目标放在 `.app` 安装目录内部

### 4. 签名与公证边界

完整签名与 notarization 不纳入首阶段，但必须预留后续接入空间。

要求：

1. 打包配置允许未来通过环境变量注入签名参数
2. 不把发布脚本写成只能服务“无签名本地构建”的结构

### 5. 依赖复杂度控制

当前技术栈以纯 Node / JS 为主，这是桌面打包的优势。

要求：

1. 首阶段避免引入复杂原生模块
2. 避免因为打包目标提前引入 SQLite 等需要额外 rebuild 的依赖

## 分阶段落地计划

### 阶段一：打通生产态启动链路

目标：

1. renderer 在不依赖 Vite 开发服务器时也能被 Electron 正常加载
2. `review-shell` 能根据开发态与生产态切换加载策略

完成标准：

1. 本地可在非 dev server 模式下启动桌面应用
2. 工作台页面能够正常打开

### 阶段二：接入 `electron-builder`

目标：

1. 增加正式打包配置
2. 生成 `macOS DMG`

完成标准：

1. 能稳定输出 `.dmg`
2. 安装后可启动应用

### 阶段三：补齐发布资源与冒烟验证

目标：

1. 完善桌面应用元信息和静态资源
2. 对安装后运行路径做最小可用验证

最少验证项：

1. 应用能启动
2. 工作台能打开
3. IPC 可用
4. 会话存储仍写入用户目录
5. 不依赖仓库开发路径

### 阶段四：为多平台与正式分发预留扩展位

目标：

1. 保持配置结构可扩展到 Windows
2. 为签名、公证和 CI 打包预留接口

完成标准：

1. 平台配置结构清晰
2. 后续新增 Windows 或签名链路时不需要重做基础架构

## 验收标准

本设计完成后的实现应满足以下验收标准：

1. 可以通过统一命令生成 `macOS DMG`
2. 安装后的应用不依赖开发服务器
3. renderer、preload、主进程路径解析在生产态稳定可用
4. 会话数据持久化仍位于用户目录
5. 工程结构没有为了首发 macOS 而破坏未来 Windows 扩展能力

## 结论

本方案建议以 `electron-builder` 为打包基线，以 `macOS DMG` 为首发交付形态，以“先打通生产态资源加载，再补正式打包配置”为实施顺序。

这一路线与当前仓库的 Electron 架构兼容度最高，能够在不打乱前后端职责边界的前提下，把现有开发态桌面工程推进到可交付软件阶段，并为未来 `Windows`、签名、公证和 CI 发布保留稳定扩展位。
