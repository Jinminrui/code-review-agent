# 可视化代码审查 Agent 设计文档

- 日期：2026-06-06
- 目标：定义一个面向 reviewer 的桌面端可视化代码审查 Agent 的 MVP 设计
- 参考：`/Users/jinminrui/open-code-review`

## 1. 目标与边界

本项目的第一版定位为一个独立桌面应用，服务于 `reviewer` 对单个变更集的代码审查场景。它不是通用仓库治理平台，也不是 GitHub/GitLab 插件，而是一个以本地仓库分支对比为输入、以可视化审查体验为核心的审查工作台。

MVP 目标如下：

1. 让 reviewer 快速理解一次分支改动做了什么。
2. 让 reviewer 快速看到高风险问题及其证据。
3. 让 reviewer 能从问题卡片直接跳到具体 diff 位置验证问题。
4. 让一次审查结果可以保存、回看、重跑失败部分。

本阶段明确不做：

1. 在线拉取 GitHub/GitLab PR。
2. 向平台自动回写评论。
3. 自动修复代码。
4. 本地模型支持。
5. 多人协作与复杂权限系统。

## 2. 设计原则

项目采用以下设计原则：

1. 确定性逻辑前置：`diff` 解析、文件筛选、行号映射、上下文裁剪等必须由工程逻辑稳定完成。
2. LLM 负责判断，不负责流程控制：模型用于理解改动与发现风险，不决定应审查哪些文件。
3. 输出结构化：前端只消费稳定的结构化审查结果，不直接依赖原始模型文本。
4. 渐进式展示：不等待全量完成，优先展示已经完成的摘要与问题。
5. 可信度优先：结果不确定时明确降级或标注，不伪造精确定位。

## 3. 总体架构

第一版采用 `Electron + TypeScript` 全栈架构，分为四层：

### 3.1 桌面壳

桌面壳负责：

1. 窗口生命周期管理。
2. 本地仓库选择与基础权限处理。
3. 审查任务的创建、取消、恢复与重跑触发。

桌面壳不直接参与审查推理，只承担应用容器与任务入口职责。

### 3.2 审查编排层

审查编排层是后端核心，使用 TypeScript 实现，负责：

1. 读取本地 git 仓库。
2. 生成分支差异。
3. 拆分审查单元。
4. 收集补充上下文。
5. 调用云端 LLM。
6. 聚合审查结果。
7. 落盘保存审查会话。

这一层借鉴 `open-code-review` 的方法论：以确定性工程能力约束审查流程，再让模型处理语义判断。

### 3.3 结构化审查模型层

该层负责定义并产出统一的数据结构，例如：

1. 改动摘要。
2. 高风险文件列表。
3. 问题卡片列表。
4. 文件级和行级定位信息。
5. 证据片段、建议和置信信号。

其目标是隔离模型输出波动，保证前端接口稳定。

### 3.4 可视化审查台

前端采用“双栏混合”主布局：

1. 左侧展示改动摘要、风险概览和问题卡片流。
2. 右侧展示文件 diff、代码上下文和问题定位详情。

交互重点是让 reviewer 在“理解改动”和“验证问题”之间快速切换。

## 4. 核心组件

后端建议拆分为六个组件：

### 4.1 Repository Adapter

职责：

1. 列出仓库分支。
2. 读取两个分支之间的 diff。
3. 读取指定文件和指定版本内容。
4. 提供基础提交信息。

该组件是与 git 交互的唯一入口。

### 4.2 Review Unit Planner

职责：

1. 将一次分支 diff 拆分为多个审查单元。
2. 按文件、目录或关联关系对改动进行分组。
3. 控制每个审查单元的上下文规模。

目标是在不遗漏问题的前提下，降低单次模型输入复杂度。

### 4.3 Context Collector

职责：

1. 收集变更文件内容。
2. 补充关联定义、调用点或测试文件。
3. 根据规则控制上下文深度与范围。

这个组件决定模型看到什么，是审查质量关键因素之一。

### 4.4 LLM Review Runner

职责：

1. 组装 prompt。
2. 调用云端 provider。
3. 处理重试、超时、限流与 token 统计。
4. 返回原始审查结果。

该组件只负责模型调用，不承担 git 或 UI 逻辑。

### 4.5 Finding Normalizer

职责：

1. 清洗模型输出。
2. 将自然语言问题转为统一 finding 结构。
3. 做行号映射与定位校正。
4. 在定位失败时降级为文件级 finding。

该组件是“让结果可信”的关键模块。

### 4.6 Review Session Store

职责：

1. 保存输入参数、执行状态和中间结果。
2. 保存最终摘要、问题卡片和按文件聚合结果。
3. 支持历史会话读取、失败恢复和局部重跑。

## 5. 核心数据流

一次 review session 的处理流程如下：

1. reviewer 选择本地仓库。
2. 应用读取可选分支与基础仓库信息。
3. reviewer 选择 `base branch` 和 `target branch` 并发起审查。
4. 系统创建 review session，记录输入参数与初始状态。
5. 后端生成 branch diff，并做第一层过滤与概览统计。
6. `Review Unit Planner` 将改动拆成多个审查单元。
7. `Context Collector` 为每个审查单元补充必要上下文。
8. `LLM Review Runner` 并发执行审查。
9. `Finding Normalizer` 规范化结果并校正定位。
10. 会话聚合器汇总整次审查结果。
11. 前端按进度渐进式展示摘要、问题卡片和 diff 详情。

渐进式展示是该方案的重要体验设计，用户不必等待所有任务全部完成才开始审查。

## 6. 审查结果模型

第一版建议统一使用如下 finding 结构：

```ts
type ReviewFinding = {
  id: string;
  severity: "high" | "medium" | "low";
  category: string;
  summary: string;
  explanation: string;
  file: string;
  startLine?: number;
  endLine?: number;
  evidence?: string;
  suggestion?: string;
  confidenceSignals: string[];
  status: "line-level" | "file-level";
};
```

其中：

1. `status` 用于区分是否成功精确定位。
2. `confidenceSignals` 用于表达可信度来源，而不是给出单一黑盒分数。

第一版建议至少支持以下信号：

1. 命中新增加或修改代码。
2. 存在明确证据片段。
3. 成功行级定位。
4. 涉及跨文件上下文推理。
5. 检测到测试缺失或保护不足。

## 7. 错误处理与边界策略

### 7.1 定位失败降级

如果问题无法可靠映射到具体行，则降级为文件级 finding，并显式标记“未能精确定位”。

### 7.2 大变更集处理

当 diff 规模过大时：

1. 先做文件级风险排序。
2. 优先审查高风险文件。
3. 其余文件可延后处理或标记为未深度审查。

系统必须诚实表达审查覆盖范围，不能假装全量完成。

### 7.3 上下文缺失提示

当仓库缺少测试文件、依赖文件、目标分支，或代码解析失败时，前端必须显式提示该 finding 的上下文限制。

### 7.4 单元级失败隔离

单个审查单元失败时：

1. 不阻塞其他单元继续执行。
2. 当前 session 标记为部分可用。
3. 支持后续只重跑失败单元。

### 7.5 隐私边界

第一版使用云端 LLM，因此产品必须清楚告知会发送的内容：

1. 分支 diff。
2. 相关代码片段。
3. 必要上下文文件内容。

并预留配置能力，例如排除敏感目录、限制上下文深度、过滤特定文件类型。

### 7.6 不做自动修复

第一版只负责发现问题、解释问题和定位问题，不执行自动改代码行为。

## 8. 前端交互设计

主视图采用双栏混合布局：

### 8.1 左栏

展示：

1. 仓库与分支信息。
2. 改动摘要。
3. 高风险文件列表。
4. 问题卡片流。
5. 执行进度与失败单元状态。

### 8.2 右栏

展示：

1. 文件 diff。
2. 代码上下文。
3. 当前问题的证据、解释与建议。

交互要求：

1. 点击问题卡片时，右侧自动滚动到对应文件与 hunk。
2. 若是文件级 finding，则定位到文件顶部并高亮相关区段。
3. 已完成单元优先可见，减少等待感。

## 9. 测试策略

### 9.1 单元测试

覆盖：

1. `Repository Adapter`
2. `Review Unit Planner`
3. `Finding Normalizer`

重点验证 diff 处理、分组逻辑、结构化映射和定位降级是否稳定。

### 9.2 集成测试

模拟从分支选择到 session 完成的完整流程，验证：

1. 状态流转。
2. 失败隔离。
3. 中间结果保存。
4. 重跑失败单元。

### 9.3 前端 E2E

至少覆盖：

1. 创建 review session。
2. 查看改动摘要。
3. 点击问题卡片跳转到 diff。
4. 展示处理中、失败和部分可用状态。

### 9.4 LLM 测试策略

默认使用 mock 或录制响应，避免测试依赖真实模型输出稳定性。真实 provider 仅做少量冒烟验证。

## 10. MVP 范围

第一版包含：

1. 选择本地 git 仓库。
2. 选择 `base branch` / `target branch`。
3. 发起一次审查 session。
4. 展示改动概览。
5. 展示改动摘要。
6. 展示问题卡片列表。
7. 点击问题后定位到右侧 diff。
8. 展示任务进度、失败单元和重跑失败单元。
9. 保存并重新打开历史 session。
10. 配置一个云端 LLM provider。

第一版不包含：

1. 在线 PR 接入。
2. 评论回写。
3. 自动修复。
4. 本地模型支持。
5. 多人协作。
6. 复杂规则引擎。

## 11. 推荐实施方向

推荐采用如下组合策略：

1. 产品架构选择 `Electron + TypeScript`。
2. 审查引擎借鉴 `open-code-review` 的“确定性工程 + LLM”思路。
3. 不复用其 Go 后端实现，而是以 TypeScript 重建审查编排与结果模型。

这样可以同时满足：

1. 快速实现桌面端体验。
2. 保持审查流程的稳定性与可解释性。
3. 为后续扩展在线 PR 接入、本地模型或更多 provider 留出清晰边界。

## 12. 成功标准

MVP 完成后，应至少满足以下标准：

1. reviewer 可以在本地仓库上完成一次完整分支对比审查。
2. 系统能稳定输出改动摘要和结构化问题卡片。
3. 至少大部分问题可以准确定位到文件和代码区间。
4. 对无法精确定位或上下文不足的结果，系统能清楚说明限制。
5. 审查结果可保存、回看，并支持局部失败重跑。
